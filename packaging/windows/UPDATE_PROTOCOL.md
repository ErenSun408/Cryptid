# 更新事务接入约束

产品向导通过 `installer-engine.nsh` 使用本协议；构建脚本生成固定文件计划，新装、原位更新、修复及卸载共用路径和文件保护。

## 文件和路径

- 每个目标、暂存和备份文件名必须来自构建时固定清单；恢复记录不能携带路径或命令。保留用户文件，不递归删除应用目录。
- 已登记且目录存在时确认原位更新，目录缺失的旧登记不拦截新装；缺少主程序的已登记目录可以修复。实际修改前再次核对登记。未登记的非空目录只允许恢复同包事务，不按文件名猜测其归属。
- `.usb-vault-update` 使用当前用户和 SYSTEM 的受保护 DACL，恢复时验证所有者与 DACL；包身份包含负载清单、helper、NSIS 源码和文件计划生成器摘要，文件编号按 ordinal 顺序固定。不同包、无身份或未知条目保留现场并拒绝覆盖。
- 应用、暂存和备份必须在同一固定磁盘卷上；目录树禁止重解析点。调用 `UpdateGuardDirectory` 固定每一条所用父目录，包括嵌套的清单子目录，并将句柄持有到所有文件操作结束；失败也调用 `UpdateReleasePaths`。
- 安装、卸载和恢复共用命名互斥及原目录中的 `.usb-vault-setup.lock`，独占且关闭时删除。已有冲突条目不会被截断或自动删除；断电遗留无法辨认的锁需要人工检查，不能换随机锁名绕过。
- 入口检查主窗口，修改前对已有产品文件和暂存文件取得读写／删除权限且仅共享删除的句柄，检测占用并阻止新启动；主程序在访问依赖、凭据或卡之前检查事务目录／锁。恢复后重新锁住实际目标，避免旧句柄继续锁着已移回暂存的新文件。

## 持久记录与恢复顺序

1. 构建时验证全部源文件 SHA-256，运行时由 NSIS CRC 检查嵌入负载；在已验证路径和私有目录中完成提取，并在取得文件句柄后替换。四字节记录只表示文件原先存在／不存在及文件事务已提交，不能包含凭据、容器或档位信息。
2. 对每个编译期条目调用 `UpdateJournaledReplace`：排他创建意图记录，使用 write-through 写入并 `FlushFileBuffers`，然后移动旧文件到备份、移动新文件到目标。每个编号在同一进程中只使用一次。
3. 全部文件（含卸载器）替换成功后刷新文件提交标记（827741442），随后发布固定卸载登记与快捷方式。此顺序取代原设想的跨文件／注册表回滚：登记失败时保留完整新文件、旧备份和事务目录，重跑同包向前完成登记，不把部分登记称为安装成功。
4. 重启或失败处理先调用 `UpdateLoadCommit`。无标记进入回滚；有效提交标记先重试固定登记，成功后才清理备份；损坏标记停止全部恢复。随后逆序调用 `UpdateRecoverFile`。不要混用会删除新文件的旧 `UpdateRollback` 或无全局提交保护的 `UpdateCommit`。
5. 未提交时，新文件移回暂存，旧文件恢复到原位置；已提交时保留新文件并精确删除备份。意图记录最后删除，因此恢复再次中断后可重试。状态矛盾、文件占用或记录损坏保留现场并报错；无意图却存在备份同样拒绝。
6. 确认全部条目与登记一致后，最后精确清理提交标记、包身份及空事务目录，目录清理时保留必要祖先句柄。未知条目不删除；当前版本未退役白名单中的文件，不执行旧卸载器，也不根据不可信运行时清单删除历史文件。

`UpdateTestCheckpoint` 仅供测试构建注入 `TerminateProcess`，产品构建不得定义。已测试进程被强制终止后的恢复和恢复再次中断；没有模拟物理断电、磁盘损坏或硬件缓存失效，不能承诺此类事件下自动恢复一定成功。
